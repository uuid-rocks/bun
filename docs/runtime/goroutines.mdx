`Bun.go(fn, ...args)` runs a function on another thread, the way Go's `go` statement does. It returns a `Goroutine`: a promise for what the function returns.

```ts main.ts icon="/icons/typescript.svg"
function countPrimes(from: number, to: number) {
  let count = 0;
  for (let n = Math.max(from, 2); n < to; n++) {
    let prime = true;
    for (let d = 2; d * d <= n; d++) {
      if (n % d === 0) {
        prime = false;
        break;
      }
    }
    if (prime) count++;
  }
  return count;
}

const counts = await Promise.all([
  Bun.go(countPrimes, 0, 250_000),
  Bun.go(countPrimes, 250_000, 500_000),
  Bun.go(countPrimes, 500_000, 750_000),
  Bun.go(countPrimes, 750_000, 1_000_000),
]);
console.log(counts.reduce((a, b) => a + b)); // => 78498
```

The four calls run at the same time on four threads. The function can also be written in place:

```ts
const total = await Bun.go(async (url: string) => {
  const response = await fetch(url);
  return (await response.text()).length;
}, "https://example.com");
```

## The thread pool

Goroutines run on a pool of threads that Bun starts as goroutines wait for one. The pool grows to as many threads as the machine has CPU cores, and at least 2. Set the `GOMAXPROCS` environment variable to 2 or more to choose another number (`UV_THREADPOOL_SIZE`, which also sizes Bun's other thread pools, takes precedence). The main thread is not part of the pool.

A goroutine runs on one thread until it settles. When it awaits, its thread runs other goroutines, so thousands of goroutines can wait on I/O or on a [channel](/runtime/channels) at once. A goroutine that computes without awaiting, or blocks in `Atomics.wait()`, keeps its thread busy. The other goroutines on that thread wait until it returns or awaits.

The pool never keeps the process alive. A goroutine keeps alive the thread that started it until it settles, unless you call `unref()` on it.

```ts
Bun.go(watchForever).unref(); // the process can exit while it runs
```

## Which functions can run

A goroutine's function runs on another thread, which has only the function's own code and the globals. So `fn` is one of these:

- **A function that uses only its parameters, what it declares, and globals.** Bun sends its source to the pool thread, which compiles it once. Globals such as `Bun`, `fetch`, `Atomics` and `structuredClone` are there. This is the usual way to start a goroutine.
- **A function that a module exports** (ES module or CommonJS). Each pool thread imports that module once, then calls the export. Use this for large code, or code that shares its module's imports and helpers with other code. When a function is exported, Bun runs it this way.

A function written in place can't use the variables of the code around it: they stay on their own thread. `Bun.go()` throws a `TypeError` with the code `ERR_GOROUTINE_NOT_SENDABLE` that names each variable and its line, and says what to do about it:

```ts
const config = { limit: 10 };
Bun.go(() => config.limit * 2);
// TypeError: Bun.go() can't run this function on another thread: it uses "config" (/app/main.ts:2),
// a variable of the code around it: pass it as an argument.
```

The advice depends on what the variable holds. For a function imported from a module, the message suggests passing that function to `Bun.go()` itself (`Bun.go(triple, x)`), for a named import from `"bun"` it suggests the `Bun` global (`Bun.sleep`), and for a helper function of the code around it, it suggests moving the helper into the function or into a module other than the entry point.

Pass values as arguments instead:

```ts
const config = { limit: 10 };
await Bun.go(config => config.limit * 2, config); // => 20
```

The same goes for an arrow function that uses the `this` or `arguments` of the code around it, and a function that uses `import.meta`. A method, a class, and a bound or native function throw `ERR_GOROUTINE_NOT_SENDABLE` too.

<Note>
  Bun checks the function as it transpiled it. The transpiler replaces a `const` that holds a literal, such as `const
  limit = 10`, with its value, so a function that uses one runs. A `const` that holds an object, or a `let`, is still a
  variable of the code around it. Pass values as arguments rather than rely on this.
</Note>

To use a module, import it inside the function. `await import()` and `require()` resolve from the file the function is written in, as they would there. Only the module's own `require` is given to the function: a parameter or variable named `require` of the code around it is a variable like any other.

```ts main.ts icon="/icons/typescript.svg"
const digest = await Bun.go(async (text: string) => {
  const { hash } = await import("./hash.ts"); // ./hash.ts next to main.ts
  return hash(text);
}, "hello");
```

TypeScript works in either form: the function runs as Bun transpiled it, and errors and stack traces name the lines of your source.

<Note>
  A function written in place is compiled again on the pool thread from its source, the way `new Function()` compiles a
  string. When code generation from strings is disallowed (`--disallow-code-generation-from-strings`), only exported
  functions and module URLs can run.
</Note>

### Modules as goroutines

`Bun.go()` also takes the URL of a module, and runs the module's default export:

```ts
const result = await Bun.go(new URL("./task.ts", import.meta.url), 1, 2);
```

Bun resolves a module URL the way `new Worker()` resolves its entry point. It resolves a relative path against the current directory, so prefer `new URL("./task.ts", import.meta.url)`.

The URL's fragment names another export. Then the calling thread doesn't import the module at all:

```ts
const count = await Bun.go(new URL("./primes.ts#countPrimes", import.meta.url), 0, 1e6);
```

### Module state

A module that a goroutine imports runs once on each pool thread. Its top-level variables belong to that thread, like thread-local storage. In a pool thread, `Bun.isMainThread` and `import.meta.main` are `false`.

A goroutine's exported function can be exported by the program's entry point. Then the entry point also runs on each pool thread that runs such a goroutine. Guard its top-level work with `import.meta.main`. Without the guard, a pool thread evaluating the entry point would call `Bun.go(double)` again, and that goroutine would wait for the entry point, which waits for it. `Bun.go()` throws `ERR_GOROUTINE_NOT_SENDABLE` there rather than wait forever, and the goroutine on the main thread rejects with that error:

```ts main.ts icon="/icons/typescript.svg"
export function double(n: number) {
  return n * 2;
}

if (import.meta.main) {
  console.log(await Bun.go(double, 21)); // => 42
}
```

## Arguments and results

Arguments and results are [structured clones](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm), as with `postMessage()`. Bun clones them even when the goroutine runs on the thread that started it.

- `SharedArrayBuffer` and `WebAssembly.Memory` are shared: both threads see the same memory.
- A [`Bun.Channel`](/runtime/channels) is shared: the goroutine uses the same channel.
- An `AbortSignal` arrives as a signal that aborts when the original does (see [Cancelling goroutines](#cancelling-goroutines)).
- Everything else is copied.

Arguments that can't be cloned, such as functions, throw a `DataCloneError` from `Bun.go()` that says which argument holds what, for example `Bun.go() argument 1 has a function at .callback, which can't be sent to another thread.` A result that can't be cloned rejects the goroutine with a `DataCloneError` that says where it is.

## Errors

If the function throws, the goroutine rejects with a copy of the error. The copy has the error's name, message, stack, `cause` and own properties such as `code`. An `AggregateError` arrives as an `AggregateError`, with copies of its `errors`, and a `DOMException` as a `DOMException` with its `name` and `code`. Stack traces of a function written in place name the lines and columns of your source, and leave out the frames of the pool itself.

```ts
try {
  await Bun.go((text: string) => JSON.parse(text), "{");
} catch (error) {
  console.log(error instanceof SyntaxError); // => true
}
```

A rejected goroutine that nothing handles is an unhandled rejection on the thread that started it, so by default the process exits, as a panic does in Go. An error that a goroutine's code throws outside of the goroutine, for example in a `setTimeout()` callback, goes to `process.on("uncaughtException")` on the main thread.

`process.exit(code)` in a goroutine ends the program with that code, as `os.Exit` does in Go. The goroutine's thread stops at once. The main thread calls `process.exit(code)` when its event loop next runs, so its `exit` listeners run; other goroutines may run until then.

## Waiting for goroutines

A goroutine is a promise. `Promise.all()` waits for several and gives you their results. Use `Promise.allSettled()` to wait for all of them even when some reject.

### WaitGroup

`Bun.WaitGroup` is Go's `sync.WaitGroup` with its `Go` method, and `errgroup`'s cancellation. `group.go(fn, ...args)` starts a goroutine the way `Bun.go()` does and counts it. `group.wait()` waits for every goroutine the group started, the ones started while it waits too, then rejects with the first error if one failed. The first error also aborts `group.signal`, with the error as its reason: pass the signal to the goroutines that should stop then.

```ts
await using group = new Bun.WaitGroup();

for (const url of urls) {
  group.go(
    async (url: string, signal: AbortSignal) => {
      const response = await fetch(url, { signal });
      if (!response.ok) throw new Error(`${url}: ${response.status}`);
      return response.text();
    },
    url,
    group.signal,
  );
}

await group.wait(); // the first error, once the other fetches were aborted and ended
```

- `new Bun.WaitGroup({ signal })` aborts `group.signal` when `signal` aborts too, so the caller can cancel the whole group.
- `await using` aborts `group.signal` and waits for every goroutine at the end of the scope, so none outlives it, even when the code in the scope throws. An error that `wait()` did not throw is thrown then.
- A goroutine the group started never causes an unhandled rejection: its error is the group's. `group.go()` returns the goroutine, which you can still await for its result.
- There is no `add()` or `done()`: `group.go()` counts a goroutine when it starts it, so the count can't go wrong.

Goroutines that started other goroutines can wait for them too: a goroutine can call `Bun.go()`.

```ts
async function sum(from: number, to: number): Promise<number> {
  if (to - from <= 1000) {
    let total = 0;
    for (let n = from; n < to; n++) total += n;
    return total;
  }
  const middle = Math.floor((from + to) / 2);
  const [left, right] = await Promise.all([Bun.go(sum, from, middle), Bun.go(sum, middle, to)]);
  return left + right;
}
```

`sum` can call itself: a function's own name is its own.

## Sharing state with a mutex

Most goroutines share nothing and talk through channels. When several goroutines must update the same memory, a `SharedArrayBuffer`, guard it with a `Bun.Mutex`, Go's `sync.Mutex`:

```ts
const mu = new Bun.Mutex();
const balance = new Float64Array(new SharedArrayBuffer(8));

await Promise.all(
  Array.from({ length: 4 }, () =>
    Bun.go(
      async (mu: Bun.Mutex, balance: Float64Array) => {
        for (let i = 0; i < 1000; i++) {
          using _ = await mu.lock();
          balance[0] += 1;
        }
      },
      mu,
      balance,
    ),
  ),
);
console.log(balance[0]); // => 4000
```

- `await mu.lock()` resolves with a lock once this thread holds the mutex. `using` unlocks it at the end of the scope, even when the scope throws; `lock.unlock()` unlocks it sooner. Only the first unlock does anything.
- Waiting for a lock does not block the thread: the thread runs other goroutines meanwhile. Waiters get the lock in the order they asked for it.
- `mu.tryLock()` returns the lock if the mutex is free, or `undefined`. `using lock = mu.tryLock()` works either way.
- `mu.lock({ signal })` stops waiting when the signal aborts, and rejects with its reason.
- A mutex is shared, not copied: pass it to `Bun.go()`, send it through a channel or post it to a `Worker`, and every thread locks the same mutex.
- A thread that ends while it holds a lock, such as a terminated `Worker`, unlocks it.

## Goroutines and channels

Pass a channel to goroutines to connect them. In this pipeline, one goroutine produces numbers, three square them, and the main thread adds them up:

```ts main.ts icon="/icons/typescript.svg"
const numbers = new Bun.Channel<number>(16);
const squares = new Bun.Channel<number>(16);

Bun.go(
  async (out: Bun.Channel<number>, count: number) => {
    for (let i = 1; i <= count; i++) await out.send(i);
    out.close();
  },
  numbers,
  100,
);

const workers = Array.from({ length: 3 }, () =>
  Bun.go(
    async (input: Bun.Channel<number>, out: Bun.Channel<number>) => {
      for await (const n of input) await out.send(n * n);
    },
    numbers,
    squares,
  ),
);
Promise.all(workers).then(() => squares.close());

let total = 0;
for await (const square of squares) total += square;
console.log(total); // => 338350
```

## Cancelling goroutines

Pass an `AbortSignal` to a goroutine to tell it to stop. In the goroutine, the signal aborts when the original aborts, with a copy of its reason, so it works with `fetch()`, channel operations and `abort` listeners there. A goroutine stops only where its code checks the signal or passes it on: nothing interrupts code that computes. A loop that computes without awaiting can check `signal.aborted` or call `signal.throwIfAborted()`: these see the abort as soon as the original aborts, and fire the signal's `abort` listeners there and then.

```ts
const controller = new AbortController();

const goroutine = Bun.go(
  async (signal: AbortSignal, urls: string[]) => {
    const pages = [];
    for (const url of urls) {
      signal.throwIfAborted();
      pages.push(await (await fetch(url, { signal })).text());
    }
    return pages;
  },
  controller.signal,
  ["https://example.com/a", "https://example.com/b"],
);

controller.abort();
console.log(await goroutine.catch(error => error.name)); // => "AbortError"
```

A signal sent over a [channel](/runtime/channels) works the same way. A signal that has already aborted arrives aborted. A reason that can't be cloned arrives as an `AbortError` `DOMException`. `AbortSignal.timeout()` and `AbortSignal.any()` work too.

A goroutine that waits on channels can wait on its signal in the same `select()`, as Go code selects on `ctx.Done()`, and can stop a `for await` loop with `channel.values({ signal })`:

```ts
const stage = Bun.go(
  async (input: Bun.Channel<number>, output: Bun.Channel<number>, signal: AbortSignal) => {
    for await (const n of input.values({ signal })) {
      const sent = await Bun.select([[output, n * n], signal]);
      if (sent.index === 1) return;
    }
    output.close();
  },
  input,
  output,
  controller.signal,
);
```

[`Bun.WaitGroup`](#waitgroup) gives a group of goroutines one signal that aborts on the first error.

## Deadlocks

When every thread waits on a channel or a mutex and nothing else can wake any of them, the program can never go on. Bun then prints what waits, and where, and exits with code 1, as Go does with `fatal error: all goroutines are asleep - deadlock!`:

```ts main.ts icon="/icons/typescript.svg"
const results = new Bun.Channel<number>();
Bun.go(async (results: Bun.Channel<number>) => {
  await results.send(1);
  await results.send(2);
}, results);

console.log(await results.receive());
console.log(await results.receive());
console.log(await results.receive()); // nobody sends a third
```

```txt
1
2
error: all goroutines are asleep - deadlock!

main thread:
  Channel.receive()
    at /app/main.ts:9:27

No thread is left that can send, receive, close or unlock for these. Set BUN_GO_DEADLOCK=0 to wait anyway.
```

Bun reports a deadlock only when it is sure: anything that could still wake a thread means there is none. That is a timer, even an unref'd one; a socket, a server, a pipe, a child process or a file watcher, even unref'd; a signal listener; `Atomics.waitAsync()`; a fetch or file read in flight; a goroutine that computes; a `Worker` that runs; a thread-safe function of a native addon; `--hot`, `--watch` or the inspector. A program that waits on a promise that nothing resolves, and not on a channel or a mutex, waits as it always did.

Set `BUN_GO_DEADLOCK=0` to turn this off. Windows doesn't detect deadlocks yet.

## Coming from Go

| Go                                                           | Bun                                                                                    |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `go f(x)`                                                    | `Bun.go(f, x)`                                                                         |
| `ch := make(chan T, n)`                                      | `const ch = new Bun.Channel<T>(n)`                                                     |
| `ch <- v`                                                    | `await ch.send(v)`                                                                     |
| `v := <-ch`                                                  | `const v = await ch.receive()`                                                         |
| `for v := range ch`                                          | `for await (const v of ch)`                                                            |
| `close(ch)`, `defer close(ch)`                               | `ch.close()`, `using ch = new Bun.Channel()`                                           |
| `select { case v := <-a: ... case b <- x: ... }`             | `await Bun.select([a, [b, x]])`, then switch on `index`                                |
| `default:` in a `select`                                     | `Bun.select(cases, { default: true })` resolves `index: -1`                            |
| `case <-time.After(d):`                                      | an `AbortSignal.timeout(ms)` case                                                      |
| `ctx, cancel := context.WithCancel(ctx)`                     | `const controller = new AbortController()`                                             |
| `case <-ctx.Done():`                                         | a `signal` case                                                                        |
| `var wg sync.WaitGroup; wg.Go(f); wg.Wait()`                 | `const wg = new Bun.WaitGroup(); wg.go(f); await wg.wait()`                            |
| `g, ctx := errgroup.WithContext(ctx); g.Go(f); g.Wait()`     | `await using g = new Bun.WaitGroup({ signal }); g.go(f, g.signal); await g.wait()`     |
| `var mu sync.Mutex; mu.Lock(); defer mu.Unlock()`            | `const mu = new Bun.Mutex(); using _ = await mu.lock()`                                |
| `mu.TryLock()`                                               | `using lock = mu.tryLock()`, `undefined` if it is held                                 |
| `atomic.AddInt32(&n, 1)`                                     | `Atomics.add(counter, 0, 1)` on a `SharedArrayBuffer`                                  |
| `runtime.GOMAXPROCS(n)`                                      | the `GOMAXPROCS` environment variable                                                  |
| `fatal error: all goroutines are asleep - deadlock!`         | the same, with each waiting operation's call site                                      |

## Tests, `--hot` and executables

- `bun test --isolate` gives each test file a new pool, so each file imports its goroutines' modules anew.
- With `--hot`, a reload ends the pool's threads. Goroutines started after the reload import the modules as they are now. Goroutines that were still running reject with `ERR_GOROUTINE_THREAD_EXITED`.
- Bundles and executables built with `bun build` work as below.

## Bundles and executables

`bun build --target=bun` and `bun build --compile` find the modules that `Bun.go()` runs, and make each one an entry point of the build. The build finds:

- an imported function: `Bun.go(countPrimes)`, a default import, or `Bun.go(primes.countPrimes)` after `import * as primes`
- a URL with a literal path: `Bun.go(new URL("./task.ts", import.meta.url))`, with or without a fragment

It writes the call with the URL of that entry point's output, and the export as the fragment:

```js main.js
Bun.go(new URL("./primes.js#countPrimes", import.meta.url), 0, 5e5);
```

So you can move the output and delete the sources. Each task module's output keeps its exports under their own names, with `--minify` too. An executable holds the task modules, so it runs from any directory.

The build can't tell which module a function comes from when it arrives any other way, as in `Bun.go(tasks[name])`. Then the bundle holds a copy of the function that no module exports. A self-contained function still runs from its source. A function that uses the bindings around it throws `ERR_GOROUTINE_NOT_SENDABLE`, and the message says what to do: pass the imported binding itself, or the module's URL with the export as its fragment. For a module named by a computed path, list the module as an entry point of the build, as for a [Worker](/runtime/workers):

```sh terminal icon="terminal"
bun build --compile ./main.ts ./tasks/*.ts --outfile app
```

A function from a package that the build leaves external is passed as it is. The package's module is imported from `node_modules` at run time.
