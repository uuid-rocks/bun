`Bun.go(fn, ...args)` runs a function on another thread, the way Go's `go` statement does. It returns a `Goroutine`: a promise for what the function returns.

```ts main.ts icon="/icons/typescript.svg"
function countPrimes(from: number, to: number) {
  let count = 0;
  for (let n = Math.max(from, 2); n < to; n++) {
    let prime = true;
    for (let d = 2; d * d <= n; d++) {
      if (n % d === 0) {
        prime = false;
        break;
      }
    }
    if (prime) count++;
  }
  return count;
}

const counts = await Promise.all([
  Bun.go(countPrimes, 0, 250_000),
  Bun.go(countPrimes, 250_000, 500_000),
  Bun.go(countPrimes, 500_000, 750_000),
  Bun.go(countPrimes, 750_000, 1_000_000),
]);
console.log(counts.reduce((a, b) => a + b)); // => 78498
```

The four calls run at the same time on four threads. The function can also be written in place:

```ts
const total = await Bun.go(async (url: string) => {
  const response = await fetch(url);
  return (await response.text()).length;
}, "https://example.com");
```

## The thread pool

Goroutines run on a pool of threads that Bun starts as goroutines wait for one. The pool grows to as many threads as the machine has CPU cores, and at least 2. Set the `GOMAXPROCS` environment variable to 2 or more to choose another number (`UV_THREADPOOL_SIZE`, which also sizes Bun's other thread pools, takes precedence). The main thread is not part of the pool.

A goroutine runs on one thread until it settles. When it awaits, its thread runs other goroutines, so thousands of goroutines can wait on I/O or on a [channel](/runtime/channels) at once. A goroutine that computes without awaiting, or blocks in `Atomics.wait()`, keeps its thread busy. The other goroutines on that thread wait until it returns or awaits.

The pool never keeps the process alive. A goroutine keeps alive the thread that started it until it settles, unless you call `unref()` on it.

```ts
Bun.go(watchForever).unref(); // the process can exit while it runs
```

## Which functions can run

A goroutine's function runs on another thread, which has only the function's own code and the globals. So `fn` is one of these:

- **A function that uses only its parameters, what it declares, and globals.** Bun sends its source to the pool thread, which compiles it once. Globals such as `Bun`, `fetch`, `Atomics` and `structuredClone` are there. This is the usual way to start a goroutine.
- **A function that a module exports** (ES module or CommonJS). Each pool thread imports that module once, then calls the export. Use this for large code, or code that shares its module's imports and helpers with other code. When a function is exported, Bun runs it this way.

A function written in place can't use the variables of the code around it: they stay on their own thread. `Bun.go()` throws a `TypeError` with the code `ERR_GOROUTINE_NOT_SENDABLE` that names each variable and its line:

```ts
const config = { limit: 10 };
Bun.go(() => config.limit * 2);
// TypeError: Bun.go() can't run this function on another thread: it uses "config" (/app/main.ts:2),
// which is neither its own nor a global. Pass it as an argument, or import it inside the function
// with `await import()`.
```

Pass values as arguments instead:

```ts
const config = { limit: 10 };
await Bun.go(config => config.limit * 2, config); // => 20
```

The same goes for an arrow function that uses the `this` or `arguments` of the code around it, and a function that uses `import.meta`. A method, a class, and a bound or native function throw `ERR_GOROUTINE_NOT_SENDABLE` too.

To use a module, import it inside the function. `await import()` and `require()` resolve from the file the function is written in, as they would there:

```ts main.ts icon="/icons/typescript.svg"
const digest = await Bun.go(async (text: string) => {
  const { hash } = await import("./hash.ts"); // ./hash.ts next to main.ts
  return hash(text);
}, "hello");
```

TypeScript works in either form: the function runs as Bun transpiled it, and errors and stack traces name the lines of your source.

<Note>
  A function written in place is compiled again on the pool thread from its source, the way `new Function()` compiles a
  string. When code generation from strings is disallowed (`--disallow-code-generation-from-strings`), only exported
  functions and module URLs can run.
</Note>

### Modules as goroutines

`Bun.go()` also takes the URL of a module, and runs the module's default export:

```ts
const result = await Bun.go(new URL("./task.ts", import.meta.url), 1, 2);
```

Bun resolves a module URL the way `new Worker()` resolves its entry point. It resolves a relative path against the current directory, so prefer `new URL("./task.ts", import.meta.url)`.

The URL's fragment names another export. Then the calling thread doesn't import the module at all:

```ts
const count = await Bun.go(new URL("./primes.ts#countPrimes", import.meta.url), 0, 1e6);
```

### Module state

A module that a goroutine imports runs once on each pool thread. Its top-level variables belong to that thread, like thread-local storage. In a pool thread, `Bun.isMainThread` and `import.meta.main` are `false`.

A goroutine's exported function can be exported by the program's entry point. Then the entry point also runs on each pool thread that runs such a goroutine. Guard its top-level work with `import.meta.main`:

```ts main.ts icon="/icons/typescript.svg"
export function double(n: number) {
  return n * 2;
}

if (import.meta.main) {
  console.log(await Bun.go(double, 21)); // => 42
}
```

## Arguments and results

Arguments and results are [structured clones](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm), as with `postMessage()`. Bun clones them even when the goroutine runs on the thread that started it.

- `SharedArrayBuffer` and `WebAssembly.Memory` are shared: both threads see the same memory.
- A [`Bun.Channel`](/runtime/channels) is shared: the goroutine uses the same channel.
- An `AbortSignal` arrives as a signal that aborts when the original does (see [Cancelling goroutines](#cancelling-goroutines)).
- Everything else is copied.

Arguments that can't be cloned, such as functions, throw a `DataCloneError` from `Bun.go()`. A result that can't be cloned rejects the goroutine with a `DataCloneError`.

## Errors

If the function throws, the goroutine rejects with a copy of the error. The copy has the error's name, message, stack, `cause` and own properties such as `code`.

```ts
try {
  await Bun.go((text: string) => JSON.parse(text), "{");
} catch (error) {
  console.log(error instanceof SyntaxError); // => true
}
```

A rejected goroutine that nothing handles is an unhandled rejection on the thread that started it, so by default the process exits, as a panic does in Go. An error that a goroutine's code throws outside of the goroutine, for example in a `setTimeout()` callback, goes to `process.on("uncaughtException")` on the main thread.

## Waiting for goroutines

A goroutine is a promise. `Promise.all()` waits for several, as a `sync.WaitGroup` does in Go. Use `Promise.allSettled()` to wait for all of them even when some reject.

Goroutines that started other goroutines can wait for them too: a goroutine can call `Bun.go()`.

```ts
async function sum(from: number, to: number): Promise<number> {
  if (to - from <= 1000) {
    let total = 0;
    for (let n = from; n < to; n++) total += n;
    return total;
  }
  const middle = Math.floor((from + to) / 2);
  const [left, right] = await Promise.all([Bun.go(sum, from, middle), Bun.go(sum, middle, to)]);
  return left + right;
}
```

`sum` can call itself: a function's own name is its own.

## Goroutines and channels

Pass a channel to goroutines to connect them. In this pipeline, one goroutine produces numbers, three square them, and the main thread adds them up:

```ts main.ts icon="/icons/typescript.svg"
const numbers = new Bun.Channel<number>(16);
const squares = new Bun.Channel<number>(16);

Bun.go(
  async (out: Bun.Channel<number>, count: number) => {
    for (let i = 1; i <= count; i++) await out.send(i);
    out.close();
  },
  numbers,
  100,
);

const workers = Array.from({ length: 3 }, () =>
  Bun.go(
    async (input: Bun.Channel<number>, out: Bun.Channel<number>) => {
      for await (const n of input) await out.send(n * n);
    },
    numbers,
    squares,
  ),
);
Promise.all(workers).then(() => squares.close());

let total = 0;
for await (const square of squares) total += square;
console.log(total); // => 338350
```

## Cancelling goroutines

Pass an `AbortSignal` to a goroutine to tell it to stop. In the goroutine, the signal aborts when the original aborts, with a copy of its reason, so it works with `fetch()`, channel operations and `abort` listeners there. A goroutine stops only where its code checks the signal or passes it on: nothing interrupts code that computes.

```ts
const controller = new AbortController();

const goroutine = Bun.go(
  async (signal: AbortSignal, urls: string[]) => {
    const pages = [];
    for (const url of urls) {
      signal.throwIfAborted();
      pages.push(await (await fetch(url, { signal })).text());
    }
    return pages;
  },
  controller.signal,
  ["https://example.com/a", "https://example.com/b"],
);

controller.abort();
console.log(await goroutine.catch(error => error.name)); // => "AbortError"
```

A signal sent over a [channel](/runtime/channels) works the same way. A signal that has already aborted arrives aborted. A reason that can't be cloned arrives as an `AbortError` `DOMException`. `AbortSignal.timeout()` and `AbortSignal.any()` work too.

## Tests, `--hot` and executables

- `bun test --isolate` gives each test file a new pool, so each file imports its goroutines' modules anew.
- With `--hot`, a reload ends the pool's threads. Goroutines started after the reload import the modules as they are now. Goroutines that were still running reject with `ERR_GOROUTINE_THREAD_EXITED`.
- Bundles and executables built with `bun build` work as below.

## Bundles and executables

`bun build --target=bun` and `bun build --compile` find the modules that `Bun.go()` runs, and make each one an entry point of the build. The build finds:

- an imported function: `Bun.go(countPrimes)`, a default import, or `Bun.go(primes.countPrimes)` after `import * as primes`
- a URL with a literal path: `Bun.go(new URL("./task.ts", import.meta.url))`, with or without a fragment

It writes the call with the URL of that entry point's output, and the export as the fragment:

```js main.js
Bun.go(new URL("./primes.js#countPrimes", import.meta.url), 0, 5e5);
```

So you can move the output and delete the sources. Each task module's output keeps its exports under their own names, with `--minify` too. An executable holds the task modules, so it runs from any directory.

The build can't tell which module a function comes from when it arrives any other way, as in `Bun.go(tasks[name])`. Then the bundle holds a copy of the function that no module exports. A self-contained function still runs from its source. A function that uses the bindings around it throws `ERR_GOROUTINE_NOT_SENDABLE`, and the message says what to do: pass the imported binding itself, or the module's URL with the export as its fragment. For a module named by a computed path, list the module as an entry point of the build, as for a [Worker](/runtime/workers):

```sh terminal icon="terminal"
bun build --compile ./main.ts ./tasks/*.ts --outfile app
```

A function from a package that the build leaves external is passed as it is. The package's module is imported from `node_modules` at run time.
